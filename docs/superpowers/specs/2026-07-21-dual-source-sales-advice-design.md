# 双通道销售情报与稳健模型建议设计

## 目标

让售前销售情报 Demo 稳定产出可用的、基于公开证据的作战卡。官网公开直连为第一路采集，Firecrawl 为第二路补充采集；模型建议失败或格式不完美时，报告仍应使用真实来源内容，而不是退回通用模板。

## 已确认的根因

1. `HybridCrawler` 在直连成功后立即返回，Firecrawl 没有执行，因此它实际上是备用而不是补充。
2. 模型层要求一次性返回完整且严格匹配的痛点与话术对象。模型输出被截断、数组数量不同或单字段类型不同，都会使 Zod 校验抛错；捕获块随后丢弃全部模型结果并使用固定规则模板。
3. 规则模板未提取来源的有效事实，只使用行业预设词，因此内容泛化。
4. 采集成功提示放在 `warnings` 中，前端将其渲染为红色错误，混淆了状态与失败。

## 方案

### 1. 双通道采集

- 先执行 Node.js 公开直连，获取目标官网页面。
- 只要配置了 Firecrawl，就继续执行 Firecrawl：抓取官网可读 Markdown，并按行业研究重点补充公开网页/新闻。
- 两路独立失败，不互相阻塞：任何一路有可用来源即可继续生成；两路都无来源才返回错误。
- 合并后按规范化 URL 与内容哈希去重；每条来源保留类型、标题、正文、抓取时间和来源链接。
- 返回 `collectionNotes`（成功/覆盖状态）与 `warnings`（影响结果的真实问题）两类信息。Firecrawl 的单路失败在直连已有结果时作为“未覆盖的补充通道”记录，不作为整页红色错误。

### 2. 证据优先的报告生成

- 新增来源摘要选择器：优先提取标题、meta description、首个有效正文段落，滤掉导航、脚本和重复短语。
- 所有规则生成的概览、信号、痛点和开场均引用实际来源摘要与来源 ID；不再以固定的“官网动态/信息分散”作为默认事实。
- 痛点一律标注“待验证”，销售话术先引用公开事实，再用问题求证，避免把推断说成事实。

### 3. 稳健的模型增强

- 模型只生成两项用户最需要的内容：`painHypotheses` 与 `talkTrack`；其余卡片保持证据生成层的稳定输出。
- 传入精简、可读、分段的证据包，而不是页面前 1,200 个字符；限制每个来源的摘要长度与总上下文。
- 接收模型返回后先提取 JSON，再做宽松解析和字段归一化（字符串/数组、缺失的非关键字段、问题数量）。
- 对可修复的小格式差异进行局部补全；只有模型完全无内容或没有任何可用字段时才采用证据生成层的建议。
- 官方 DeepSeek 使用非思考模式和 JSON 输出请求。调用响应、完成原因与解析阶段仅记录为不含密钥的诊断信息。

### 4. 前端反馈

- 成功状态使用中性/绿色信息块，真实失败/降级才使用红色告警。
- 若模型建议没有采用，页面明确说明“已基于采集证据生成建议”，并不暗示 API 或整份报告失败。
- 仍展示来源链接，方便用户核验。

## 验收标准

1. 配置 Firecrawl 时，直连成功后 Firecrawl 仍会被调用；两路结果合并去重。
2. 单一路失败不会阻断另一路的可用结果。
3. DeepSeek 官网接口成功且返回内容时，报告展示模型生成的至少一条“业务核心潜在痛点”和完整“销售谈话建议”。
4. 模型格式轻微偏差或不可用时，报告仍展示从真实来源标题/摘要生成的、企业相关的痛点和话术，不出现固定泛化措辞。
5. 页面不再把“直连采集成功”等正常状态显示为红色错误。
6. 单元测试覆盖双通道合并、模型输出归一化/降级和状态分类；通过构建与一次真实官网端到端请求验证。

## 非目标

- 不绕过登录、反爬、付费墙或网站访问规则。
- 不把公开资料推断表述为已证实的客户内部事实。
- 本次不增加数据库、账号体系或异步任务队列。
