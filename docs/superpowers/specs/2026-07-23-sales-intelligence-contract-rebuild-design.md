# 销售研究 Agent 信息合同与完整性重构设计

## 1. 目标

把当前“抓到什么就临时写什么”的研究流程，重构为“先定义销售必须得到的答案，再围绕缺口采集、整理和验收”的销售研究系统。

完成后的 Demo 必须同时满足：

1. 对 B2B 销售有直接行动价值，而不是泛泛的公司摘要。
2. 同一家公司重复运行时，核心报告结构稳定。
3. 已经生成且通过验证的字段不会因为其他字段缺失而被整体丢弃。
4. 没有证据时不编造，但必须明确记录“未找到”“待验证”或“信息冲突”。
5. 所有正式字段在 UI 中有唯一、固定的展示位置。
6. 所有事实、业务信号和推断均可追溯到公开来源。

## 2. 核心产品原则

### 2.1 完整不等于强行填满

“完整”指销售需要回答的每个问题都有明确状态，而不是模型必须编出答案。字段状态统一为：

- `verified`：公开证据直接支持的事实。
- `inferred`：由一个或多个公开信号推导出的待验证判断。
- `insufficient`：已经定向查找，但没有找到足够证据。
- `conflicting`：不同来源出现矛盾，不能给出确定结论。

### 2.2 逐字段验收

模型返回的每个字段单独进行：

1. 结构校验。
2. 中文可读性校验。
3. 来源编号校验。
4. 证据相关性校验。
5. 销售方产品关联校验。

任何字段不合格时只删除或补采该字段，不得丢弃同批次中已经合格的其他字段。

### 2.3 事实、信号、推断、行动分层

- 事实：公司公开说明的业务、产品、客户、市场、产能等。
- 信号：扩产、新品、招聘、合作、融资、出海、客户案例等变化。
- 推断：信号可能带来的痛点、影响和需求，必须标注“待验证”。
- 行动：销售应该联系谁、怎么开场、问什么、推进什么。

UI 不允许把四类内容混在同一个卡片里。

## 3. 销售信息合同

| 模块 | 信息字段 | 对销售的价值 | 优先来源 | 无结果时 |
|---|---|---|---|---|
| 01 销售结论 | 联系建议 | 判断是否值得投入时间 | 后续模块综合 | 显示“证据不足，建议先补充调研” |
| 01 销售结论 | 推荐理由 | 解释为什么现在联系 | 业务信号、产品匹配 | 不生成通用理由 |
| 01 销售结论 | 三个关键客户信号 | 提供开场依据 | 动态、产品、产能、合作 | 展示实际找到的数量 |
| 01 销售结论 | 优先联系角色 | 明确找谁 | 官网团队、招聘、业务模式、产品性质 | 标记“待确认角色” |
| 01 销售结论 | 优先切入机会 | 给出第一通电话的主题 | 痛点、潜在需求、产品匹配 | 不使用行业通用痛点 |
| 01 销售结论 | 建议下一步 | 将研究转成动作 | 沟通策略 | 使用销售方提供的 CTA 兜底 |
| 02 客户情报 | 公司概况 | 快速认识客户 | 官网介绍、工商、权威资料 | 记录信息缺口 |
| 02 客户情报 | 产品与服务 | 判断客户在卖什么 | 产品页、解决方案页、目录 | 记录信息缺口 |
| 02 客户情报 | 目标客户与市场 | 判断客户服务谁、在哪里经营 | 客户案例、市场页、公司介绍 | 记录信息缺口 |
| 02 客户情报 | 商业模式 | 理解其获客和交付方式 | 产品、服务、渠道、客户案例 | 不从行业常识猜测 |
| 02 客户情报 | 产品定位 | 判断品质、价格和差异化方向 | 产品文案、品牌页、案例 | 不从口号过度推断 |
| 02 客户情报 | 规模与能力 | 判断合作体量 | 产能、员工、工厂、资质、市场覆盖 | 展示已找到的维度 |
| 02 客户情报 | 近期动态 | 判断联系时机 | 官网新闻、公告、权威媒体 | 明确“未找到近期动态” |
| 03 机会判断 | 业务触发信号 | 说明为什么现在可能有机会 | 扩产、新品、招聘、合作、出海等 | 不生成机会 |
| 03 机会判断 | 潜在痛点 | 把信号转为待验证问题 | 至少一个具体业务信号 | 必须标记 `inferred` |
| 03 机会判断 | 业务影响 | 说明问题为什么值得解决 | 信号与业务链路分析 | 不写无法解释的空泛影响 |
| 03 机会判断 | 产品能力匹配 | 判断我方能否切入 | 客户信号 + 销售方产品档案 | 明确匹配依据或不匹配 |
| 03 机会判断 | 当前方案/竞争 | 判断替换、补充或新购 | 官网、案例、权威外部资料 | 记录为信息缺口 |
| 03 机会判断 | 验证问题 | 把推断变成销售可问的问题 | 每条痛点一一对应 | 每条推断至少一个问题 |
| 03 机会判断 | 置信度 | 防止把推断当事实 | 证据数量、质量和一致性 | 低/中/高并说明原因 |
| 04 沟通作战 | 推荐联系对象 | 找到正确角色 | 业务性质、团队和决策链推断 | 标记待确认 |
| 04 沟通作战 | 沟通目标 | 规定第一次沟通要验证什么 | 机会判断 + 销售 CTA | 不使用空泛目标 |
| 04 沟通作战 | 30 秒开场 | 销售可直接使用 | 客户信号 + 我方产品 | 不背诵产品功能 |
| 04 沟通作战 | 价值表达 | 建立客户信号与我方能力的桥梁 | 产品档案 + 客户信号 | 不虚构产品效果 |
| 04 沟通作战 | 发现型问题 | 发现真实需求 | 事实、信号、痛点和决策链 | 3 至 5 个，带提问目的 |
| 04 沟通作战 | 异议与回应方向 | 帮助销售准备阻力 | 当前信息缺口和风险 | 只写回应方向，不编造客户异议 |
| 04 沟通作战 | 证明材料 | 提醒销售准备案例、资质和数据 | 销售方档案 | 未提供时不显示 |
| 04 沟通作战 | 下一步 | 推动进入可验证的小范围动作 | 销售 CTA、客户成熟度 | 明确责任人与动作 |
| 04 沟通作战 | 沟通禁区 | 防止错误假设 | 低置信度推断和信息缺口 | 至少列出最关键风险 |
| 报告底部 | 主要参考链接 | 让需要核对的人可以打开原页面 | 本次最重要的官网、产品和动态页面 | 只展示 3 至 5 个链接 |

## 4. 采集架构

### 4.1 研究计划

每次运行先生成固定研究任务：

1. 公司与身份。
2. 产品与服务。
3. 客户与市场。
4. 商业模式与能力。
5. 近期动态。
6. 业务触发信号。
7. 决策角色线索。
8. 当前方案与竞争线索。

### 4.2 双通道采集

1. Node.js 直连优先抓取首页及官网内页。
2. Firecrawl 始终作为第二阶段补充，不是只在直连失败时备用。
3. 两个通道分别保存已完成结果，任何一路超时都不得清空另一路数据。
4. 单页设置超时；整个通道使用允许完成已启动页面的软截止时间。
5. 每类最多先采集两条高价值页面；字段仍不足时再按缺口补采。

### 4.3 外部来源

官网事实要求同域。权威媒体、行业报道、工商信息和公开招聘允许进入，但必须同时满足：

1. 公司名称、品牌、官网或其他身份信号与目标公司一致。
2. 来源类型可识别。
3. 内容与信息合同中的具体字段相关。
4. 外部来源不得替代官网对公司自身产品和定位的正式表述。

### 4.4 来源选择

不再使用单一总分把来源混排。每个信息类别分别选择：

- 官网核心事实：1 至 3 条。
- 产品与服务：1 至 3 条。
- 动态与业务信号：最多 5 条。
- 权威外部补充：最多 3 条。

总来源数量可以达到 20 条，但模型每次只接收与当前任务字段有关的证据包。

## 5. 模型整理架构

模型不再一次生成整份大 JSON，而是分为三个稳定阶段：

### 5.1 事实抽取

输入分类证据，输出：

- 公司与业务事实。
- 产品与服务。
- 客户与市场。
- 商业模式和能力。
- 近期动态。
- 业务触发信号。

### 5.2 机会分析

输入事实、信号和销售方完整产品档案，输出：

- 潜在痛点。
- 业务影响。
- 产品匹配。
- 当前方案/竞争信息。
- 验证问题。
- 置信度。

### 5.3 沟通作战

输入已经验收的事实和机会，输出：

- 联系角色。
- 沟通目标。
- 开场话术。
- 价值表达。
- 发现型问题。
- 异议回应方向。
- 下一步。
- 沟通禁区。

每个阶段均采用逐字段合并。模型第一次漏掉字段时，只对缺失字段进行一次修复调用，不重写已经合格的字段。

## 6. 完整性质量门

### 6.1 禁止规则

- 禁止因一个字段缺失而丢弃整个模块。
- 禁止因一条引用错误而丢弃整次模型调用。
- 禁止用通用销售建议填充客户专属字段。
- 禁止把网页导航、页脚和整页原文当作结论。
- 禁止把销售方产品名称自动解释成未经提供的功能。

### 6.2 可交付报告最低标准

报告必须至少包含：

1. 一个已验证的公司事实。
2. 一个产品、服务或业务能力事实。
3. 一个可以支撑联系理由的具体业务信号；若没有则明确建议暂缓个性化触达。
4. 一个基于信号的待验证机会，或明确“当前无足够机会信号”。
5. 三个与当前客户事实相关的发现型问题。
6. 一个明确下一步。
7. 每个事实和信号均有来源。

不足最低标准时不返回空报告，而返回“研究未达标”报告，明确缺失字段和建议补充的材料。

## 7. UI 信息架构

### 7.1 视觉方向

参考用户提供的首页风格：

- 白色主背景。
- 深墨绿色单一强调色。
- 低饱和浅绿辅助面。
- 极轻阴影和细边框。
- 克制圆角。
- 清晰、专业的现代中文无衬线字体。
- 留白充足但不产生大面积空洞。

不照搬参考图中的居中巨型标题和单层表单排版。报告页定位为高级 B2B 情报工作台，强调信息层次和阅读效率。

### 7.2 页面骨架

- 桌面端保留固定左侧主导航。
- 正文宽度控制在 1180 至 1280px。
- 报告头展示客户名称、本次销售产品、采集时间和报告状态。
- 四个模块使用粘性横向目录。
- 正文字号 15 至 16px，行高不低于 1.7。
- 信息卡片只承载一种语义：事实、判断或行动。
- 移动端转为单列，目录横向滚动。

### 7.3 四个模块

#### 01 销售结论

排列顺序：

1. 联系建议。
2. 推荐理由。
3. 三个关键客户信号。
4. 最优机会。
5. 推荐联系角色。
6. 建议下一步。

采用一张主结论面板和两列行动卡，不重复展示完整公司介绍。

#### 02 客户情报

排列顺序：

1. 公司概况。
2. 产品与服务。
3. 客户与市场。
4. 商业模式。
5. 产品定位。
6. 规模与能力。
7. 近期动态。
8. 信息缺口。

事实卡片保持干净，不显示逐条来源编号；近期动态使用时间线。

#### 03 机会判断

每个机会使用统一纵向链路：

`公开信号 → 待验证痛点 → 业务影响 → 我方能力匹配 → 验证问题 → 置信度`

不得把链路节点拆散到多个无关联卡片中。

#### 04 沟通作战

按照实际通话流程排列：

1. 推荐联系对象。
2. 沟通目标。
3. 30 秒开场。
4. 价值表达。
5. 发现型问题。
6. 证明材料。
7. 异议与回应方向。
8. 建议下一步。
9. 沟通禁区。

开场话术使用全宽重点面板，问题使用编号列表并显示提问目的。

#### 报告底部参考链接

报告正文不设置“证据来源”模块，不显示逐条来源按钮、证据状态面板、支撑原文和采集诊断。只在整份报告底部展示 3 至 5 个最重要的参考链接：

1. 公司官网或公司介绍页。
2. 主要产品或服务页。
3. 支撑关键业务变化的动态或新闻页。
4. 必要时补充一条权威外部报道。

链接只显示清晰标题和域名，不展示技术字段、长 URL、原文摘录或内部来源编号。

## 8. 数据模型调整

新报告数据按以下顶层对象组织：

- `salesVerdict`
- `customerIntelligence`
- `opportunityAnalysis`
- `conversationPlan`
- `qualityAudit`（仅供后台校验和开发诊断，前台不展示）
- `coverage`
- `sources`
- `metrics`

每个业务字段使用统一结构：

```ts
type ResearchField<T> = {
  value?: T;
  status: "verified" | "inferred" | "insufficient" | "conflicting";
  sourceIds: string[];
  note?: string;
};
```

历史报告保留兼容读取层，旧 `Battlecard` 在读取时转换为新报告视图，不直接删除用户已有历史。

## 9. 可观测性

每次运行记录：

- 直连采集来源数。
- Firecrawl 基础采集来源数。
- Firecrawl 缺口补采来源数。
- 每类证据数量。
- 被过滤来源及原因。
- 每个信息合同字段的状态。
- 每个模型阶段成功、部分成功或失败。
- 被拒绝字段及拒绝原因。

普通用户只看到销售报告正文和底部 3 至 5 个主要参考链接；字段状态、完整证据和采集诊断仅保存在后台与开发日志中。

## 10. 测试与验收

### 10.1 单元测试

- 任一策略字段缺失时，其他合格字段仍被保留。
- 一个来源引用错误时，仅该字段失败。
- 直连超时时，Firecrawl 已完成结果仍保留。
- Firecrawl 超时时，直连已完成结果仍保留。
- 经过身份核验的外部新闻可以进入报告。
- 无法确认归属的外部来源被拒绝。
- 每个信息合同字段均有状态。
- 旧报告可以转换并展示。

### 10.2 UI 测试

- 完整报告的每个字段都有唯一位置。
- 数组中的所有项目均显示。
- 机会链路保持在同一卡片中。
- 报告底部只展示 3 至 5 个主要参考链接。
- 正文不出现逐条来源按钮、原文、证据编号或技术状态。
- 缺失信息集中出现在对应模块的简短信息缺口说明中，不生成大量空卡片。
- 1920px、1366px、平板和手机宽度均可正常阅读。

### 10.3 真实网站回归

至少选择：

1. 有清晰官网结构的制造企业。
2. 官网内容稀疏的传统企业。
3. 有较多新闻和外部报道的企业。

每个网站连续运行两次，比较核心字段覆盖度。结构必须一致；因公开数据变化产生的内容差异必须能够由采集诊断解释。

## 11. 非目标

- 当前 Demo 不承诺自动找到私人手机号或邮箱。
- 当前 Demo 不进行需要登录的 LinkedIn、公众号或付费数据库采集。
- 当前 Demo 不把未核实的行业常识包装成客户事实。
- 当前 Demo 不在本轮实现 CRM 写回、团队协作和复杂权限系统。
