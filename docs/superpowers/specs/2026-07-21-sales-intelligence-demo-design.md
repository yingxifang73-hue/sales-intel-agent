# 售前销售情报 Agent Demo 设计规格

## 1. 产品结论

Demo 定位为“证据型会前销售作战卡”，不是通用公司百科，也不自动替销售发消息。

核心承诺：用户录入自己卖什么，再输入目标公司官网，系统在一次研究任务中完成公开信息采集、证据整理、销售推理和结构化作战卡生成。

主链路固定为：

```text
目标公司
→ 搜索与网页采集
→ 证据抽取和去重
→ 结合卖方产品进行销售推理
→ 生成结构化作战卡
```

首批体验用户来自电商、外贸、AI、制造业和学生群体。由于行业分散，Demo 使用一个通用研究核心，通过行业预设改变搜索问题和关注信号，不为每个行业建立独立 Agent。学生属于体验者身份，不单独形成行业预设。

## 2. 目标与非目标

### 2.1 Demo 目标

- 让首次使用者在 3 分钟内完成输入，并得到一份可直接用于电话或拜访准备的报告。
- 所有事实性判断必须能回到可点击的公开来源。
- 明确区分“公开事实”“基于事实的销售假设”“当前未知”。
- 将研究结果映射到卖方产品，而不是生成适用于所有公司的通用痛点。
- 收集每份报告的有用性、错误点和过泛反馈，为下一轮选择真正的垂直行业。

### 2.2 非目标

- 不自动发送邮件、私信、短信或发起外呼。
- 不接入 CRM、企业微信、飞书、Slack 或日历。
- 不抓取需要登录、付费或绕过访问控制的 LinkedIn、微信公众号、企查查、天眼查等内容。
- 不做地图圈选、批量找公司和拜访路线规划。
- 不生成复杂 PDF；首版只提供网页报告、复制和浏览器打印。
- 不使用五到六个自治 Agent 串行协作；首版为单一可观测流水线。

## 3. 目标用户与行业预设

### 电商预设

关注渠道结构、产品与 SKU、品牌定位、流量与内容、履约与供应链、招聘和业务扩张信号。

### 外贸预设

关注出口市场、多语言站点、产品认证、展会、经销渠道、海外服务能力、招聘和国家/地区风险提示。

### AI 预设

关注产品层级、模型或技术栈、应用场景、客户案例、融资与招聘、近期发布、生态合作和合规表述。

### 制造业预设

关注产品目录、产能与工厂、认证、设备与工艺、经销网络、扩产招聘、招投标、展会和数字化建设信号。

### 通用预设

当用户无法判断行业时，关注公司定位、产品服务、目标客户、商业模式、近期动态、招聘和潜在业务变化。

## 4. 用户流程

### 4.1 访问控制

首批体验通过一个共享邀请码进入，以控制 API 成本。验证成功后设置 HttpOnly 会话 Cookie；邀请码只存在服务端环境变量中。

### 4.2 卖方档案

用户首次录入并可在浏览器中保存：

- 产品或服务名称，必填。
- 一句话价值主张，必填。
- 主要解决的问题，1–5 条，必填。
- 理想客户类型，必填。
- 代表性案例或证明，可选。

卖方档案默认只保存在当前浏览器 localStorage；发起研究时随请求提交。

### 4.3 目标公司

每次研究填写：

- 公司官网 URL，必填。
- 行业预设，必填，默认“通用”。
- 对方角色，可选。
- 本次会议目标，可选。
- 已知背景，可选，最多 1,000 个汉字。

### 4.4 研究进度

页面展示真实流水线阶段：

1. 识别目标公司与站点结构。
2. 搜索并采集公开来源。
3. 清洗、去重和抽取证据。
4. 结合卖方产品生成销售判断。
5. 校验引用并生成作战卡。

任务通过同一 HTTP 请求流式返回 NDJSON 事件，不引入消息队列或后台任务系统。

### 4.5 结果与反馈

完成后展示作战卡。用户可以复制报告、打开来源、浏览器打印，并选择“有用”“有错误”“太泛”。选择后可填写一条短评。

## 5. 作战卡结构

### 5.1 60 秒客户速览

用不超过 180 个汉字解释公司做什么、主要客户是谁、近期最值得注意的变化。事实句必须带引用。

### 5.2 关键触发信号

最多 3 条。每条包含事件、时间、为什么与本次销售有关、来源和置信度。

### 5.3 潜在痛点假设

最多 3 条。必须显示为“假设”，并包含支持证据、反证或不确定性，以及会议中应如何验证。

### 5.4 产品切入映射

最多 3 条，将客户信号或假设映射到卖方能力、可表达的价值和可引用案例。没有案例时明确显示“缺少案例证明”，不得虚构。

### 5.5 推荐提问

固定生成 5 个发现式问题，覆盖现状、影响、优先级、决策和下一步。问题应帮助验证痛点，不把未经确认的假设说成事实。

### 5.6 开场建议

生成约 30 秒的自然开场，引用一个最可信的公开信号，并以提问结束。

### 5.7 风险与未知

列出最多 5 条当前无法确认的信息、容易误判的内容和不应贸然表达的话。

### 5.8 来源

列出标题、URL、发布日期或抓取时间、来源类型。每个事实引用的 `sourceIds` 必须全部在来源列表存在。

## 6. 数据与推理边界

### 6.1 来源优先级

1. 目标公司官网、官方新闻、产品页、招聘页和公开 PDF。
2. 政府、监管机构、招投标和行业协会的公开页面。
3. 可信新闻媒体与合作伙伴官方页面。
4. 其他公开网页，仅作为补充。

### 6.2 证据模型

每条证据包含：

- `id`
- `claim`
- `sourceIds`
- `evidenceText`
- `publishedAt`
- `kind`: `fact | signal`
- `confidence`: `high | medium | low`

销售假设与证据分开存储。任何事实性输出没有有效 `sourceIds` 时，引用校验必须让任务失败并重试一次；第二次仍失败则移除该事实，不允许无来源展示。

### 6.3 去重

- URL 先移除追踪参数、标准化协议和尾部斜杠。
- 相同规范 URL 只保留一次。
- 正文使用 SHA-256 内容哈希去重。
- 相同事实由多个来源支持时合并 `sourceIds`，不重复生成结论。

### 6.4 安全与合规

- 仅允许 `http` 和 `https` URL。
- 拒绝 localhost、私有 IP、链路本地地址和本机文件协议，防止 SSRF。
- 不尝试绕过登录、验证码、付费墙或 robots/网站访问控制。
- 报告页明确提示“公开信息可能过期，销售假设需在沟通中确认”。
- 用户提供的会议背景可能含敏感信息；Demo 数据库最多保存 30 天，服务启动时清理过期记录，并提供按运行 ID 删除的内部脚本。

## 7. 技术设计

### 7.1 技术栈

- Node.js 24.14.0。
- Next.js 16.2.10、React 19.2.7、TypeScript 7.0.2。
- Tailwind CSS 4.3.3。
- Zod 4.4.3 作为请求、LLM 输出和报告结构的唯一运行时校验层。
- OpenAI JavaScript SDK 6.48.0 调用 OpenAI-compatible Chat Completions 接口。
- Firecrawl JavaScript SDK 4.30.1 调用托管搜索、Map 和抓取 API。
- better-sqlite3 12.11.1 保存研究运行和反馈。
- Vitest 4.1.10、Testing Library 16.3.2、Playwright 1.61.1。

### 7.2 模块边界

- `domain`：输入、来源、证据、报告和进度事件类型。
- `research`：行业预设、查询规划、URL 安全、采集、标准化和去重。
- `intelligence`：证据抽取、销售推理、引用校验和报告合成。
- `providers`：Firecrawl 与 OpenAI-compatible 客户端；业务层只依赖接口。
- `storage`：SQLite 初始化、运行和反馈仓储。
- `app`：访问控制、输入流程、研究流式接口和报告展示。

### 7.3 错误处理

- 单个外部来源抓取失败不会终止任务；保留成功来源并展示缺失提示。
- 目标官网完全不可访问且外部搜索少于 2 个有效来源时，任务返回 `INSUFFICIENT_SOURCES`，不生成幻觉报告。
- LLM JSON 解析或结构校验失败时，用同一上下文进行一次修复重试。
- Firecrawl 或 LLM 超时返回明确阶段和可重试提示。
- 客户端断开时停止继续写入响应，但已经发生的外部调用不保证取消。

## 8. 开源复用策略

### 8.1 可以复用

- 借鉴 GPT Researcher 的 planner/executor/publisher 思路、研究问题拆解和引用追踪。
- 通过 Firecrawl 的托管 API/SDK使用搜索、Map 与抓取能力。
- 后续可在独立适配器中接入 Crawl4AI 或 browser-use 作为替代/兜底。

### 8.2 不直接复制

- 不复制其他产品的品牌、名称、页面视觉、营销文案、提示词和报告全文结构。
- 不整仓复制 GPT Researcher、Firecrawl 或 browser-use 前后端；Demo 自己实现小型领域流水线。
- 不把 Firecrawl 的 AGPL 服务端源码嵌入闭源 Demo。首版仅调用其托管 API，避免其网络分发义务影响本项目。

### 8.3 许可证记录

- GPT Researcher：Apache-2.0，可修改和商业使用，但复制代码时必须保留许可证、版权/NOTICE 和修改说明。
- browser-use：MIT，复制实质代码时必须保留版权和许可声明。
- Crawl4AI：Apache-2.0，要求同 GPT Researcher。
- Firecrawl 服务端：AGPL-3.0；若未来自托管并修改后向网络用户提供服务，需要重新进行许可证评估和履行源码提供义务。

本节是工程风险控制，不构成正式法律意见。上线收费前应保留第三方组件清单并由熟悉开源许可的人复核。

## 9. 验收标准

- 在 20 个跨行业测试域名中，至少 16 个成功生成报告。
- 成功任务至少包含 5 个去重来源，其中至少 2 个来自目标公司官方域名；官网信息不足时允许降级，但必须显式提示。
- 报告所有 `fact` 和 `signal` 的 `sourceIds` 都引用存在的来源；自动化测试要求 100%。
- 单份报告最多 3 个触发信号、3 个痛点假设、3 个产品映射、5 个问题和 5 个风险。
- 常规任务中位完成时间不超过 90 秒，95 分位不超过 180 秒。
- 单次完整研究的外部服务成本目标不超过人民币 3 元；每次运行记录调用次数与 token 用量（若供应商返回）。
- 手机宽度 390px 与桌面宽度 1440px 均可完整使用，无横向滚动。
- 30 位体验用户中，至少 70% 的已提交反馈将报告标记为“有用”；同时收集行业、错误类型和过泛原因。

## 10. Demo 后的决策规则

- 若某一行业占有效使用的 40% 以上，下一轮为该行业增加专属来源和评分规则。
- 若“太泛”超过 25%，优先增强卖方档案、会议角色和产品案例输入，不先增加更多爬虫。
- 若“有错误”超过 15%，优先优化来源优先级、证据抽取和引用校验。
- 若报告有用但复用率低，下一轮增加历史报告、定时刷新或 CRM 集成。
- 地图批量找公司作为独立第二产品验证，不与本 Demo 混在同一实施计划中。
